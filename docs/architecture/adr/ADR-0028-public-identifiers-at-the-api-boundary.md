# ADR-0028: Use immutable public keys at the API boundary

Date: 2026-09-24

Status: accepted

## Context

Database UUIDs are internal relational identifiers. Console routes and responses need stable, readable identities.

## Decision

Use a positive immutable integer per domain table, generated by its own
PostgreSQL sequence with uniqueness and positivity constraints. Format public
keys centrally as `PREFIX-number`. Enforce uppercase, no leading zero, and the
positive PostgreSQL integer range. Mutation triggers protect public numbers.

| Entity | Prefix |
| --- | --- |
| Organization | ORG |
| User | USR |
| Project | PRJ |
| Feature | FEAT |
| StorageObject | OBJ |
| ReviewReport | RPT |
| ReviewFinding | FND |
| FindingReview | FREV |
| ReportSource | SRC |
| ReportAttachment | ATT |
| FindingEvidence | EVD |

Existing HTTP endpoints accept only public keys. Invalid/wrong-prefix keys yield
400; unknown or invisible resources yield 404. JWT subjects are User public keys.
Auth responses carry userKey, username and organizationKey, never a project.
Resource responses use publicKey and relationship keys, never domain UUIDs.

Resolve keys under the authenticated organization and requested parent before
using UUIDs internally. The frontend never derives public keys from UUIDs or
stores UUIDs. Report-related prefixes reserve database identity only; they do
not define ingestion/history endpoints. Retain the old finding/review sequence
values when migrating so existing FND/FREV keys are not reused.

## Consequences

Public keys are enumerable identifiers, not authorization. Contract tests verify isolation, parent-child consistency and absence of UUID leakage.
